# Control：组件运行与黑板通信设计记录

本文详细记录本次讨论形成的设计方向：组件获取自身依赖的输入快照，使用私有状态完成更新，
再通过黑板发布结果；小型数据优先采用经目标平台确认无锁的原子操作，耗时 I/O 与控制周期隔离。

这是控制模块的设计记录。下文分别说明已确定的方向、候选交接机制和编写时的代码现状；
结构示意不代表接口已经实现，也不新增全仓库工程约束。

## 1. 工况与目标

当前讨论采用以下工况：

| 工作 | 频率 | 对应间隔 |
| --- | --- | --- |
| 相机输入 | 最多 120 fps | 最高帧率下约 8.33 ms 一帧 |
| 舵机更新 | 333 Hz | 约 3.00 ms 一轮 |
| 记录与存储 | 根据数据到达和存储能力执行 | 不能让文件同步延迟进入控制周期 |

这些频率描述数据产生和消费的节奏，不保证读写操作恰好错开。即使复制的数据很少，
持锁线程也可能在临界区中被调度出去，所以“硬件来得及完成复制”不能作为无等待的保证。

设计目标是减少控制路径上的等待，控制每轮工作的时间和资源开销，并明确输入的新鲜程度。
性能评估同时关注控制周期抖动、最大耗时和超期次数，不能只看平均吞吐或平均帧率。

## 2. 已确定的整体方向

| 部分 | 职责 |
| --- | --- |
| `Component` | 封装自身配置、输入依赖、输入快照、内部状态和一轮更新行为 |
| 组件运行循环 | 按周期或数据事件触发更新，处理停止请求和运行状态 |
| 运行管理器 | 创建和连接组件，管理执行线程，停止并等待线程退出 |
| `BlackBoard` | 提供类型明确的数据槽位和发布、读取接口，承担跨线程数据交接 |
| 记录组件 | 接收记录数据，完成格式化、文件写入和持久化同步 |

核心执行过程是：

```text
获取依赖并形成私有输入快照
    → 使用本轮输入和自身状态执行 update
    → 发布本轮输出
```

每个组件可以独立运行，不要求所有组件依次完成 `update()` 后才进入下一轮。
消费者使用当前可用的结果，不必等待生产者完成下一轮计算。

```mermaid
flowchart LR
    V["视觉组件：最多 120 fps"] -->|发布目标| B["BlackBoard：各数据通道"]
    I["IMU 输入与估计"] -->|发布姿态| B
    B -->|读取本轮依赖快照| C["控制与舵机组件：333 Hz"]
    C -->|发布控制状态| B
    C -->|非阻塞提交记录| Q["有界记录队列"]
    Q --> R["记录线程：格式化、写入、同步"]
```

图中表示一种可选的线程划分，不固定预测、姿态控制、舵机映射必须拆成几个组件。
轻量且有紧密先后关系的计算可以处于同一个执行线程，耗时或可能阻塞的工作独立运行。

## 3. Component、循环与线程的关系

### 一轮更新与持续运行

`update()` 表示组件的一轮工作，完成后返回。持续运行的循环由通用运行逻辑提供，
子类实现自身的输入获取、更新和输出发布行为。

以下只说明执行结构，省略具体错误返回和生命周期接口：

```text
run(stop, trigger):
    初始化组件
    while 未收到停止请求:
        等待周期或输入事件
        获取依赖，保存为本轮输入
        执行 update，生成本轮结果
        发布有效结果
    完成退出操作
```

对于周期组件，计时循环可以作为基类的公共实现；对于由新数据触发的组件，
等待输入事件的方式可以由对应执行策略提供。这里暂不固定最终的函数签名和返回类型。

### 组件可以并行，线程按工作特征划分

组件本身是功能边界，线程是执行资源。需要独立节奏或隔离阻塞的组件可以各自运行，
多个耗时可控的组件也可以有意放在同一线程中执行。

相机与控制循环的频率不同，可以独立运行。姿态换算、预测、映射等计算是否拆到不同线程，
取决于它们的耗时、数据依赖和延迟预算，不由类的数量决定。

如果预测已经成为独立运行的组件，消费者读取它发布到黑板的结果，
不能同时继续直接调用同一个预测对象的 `update()`，否则会让内部状态再次跨线程共享。

### MainLoop 的去留

原有 `MainLoop` 类可以被通用运行循环和运行管理器替代。
循环调度、停止和线程生命周期这些职责仍然存在，但不需要集中持有所有具体业务对象，
也不需要在一个全局循环中按顺序调用所有业务更新。

运行管理器保证组件构造完成后才启动线程，停止时先发出停止请求，等待线程退出，
再销毁组件及其依赖。共享黑板、设备适配对象的生命周期覆盖使用它们的组件。

停止请求是协作式的；`stop_token` 本身不会中断正在执行的文件写入、驱动调用或普通休眠。
退出响应时间仍取决于等待方式和组件正在执行的操作。

## 4. 私有快照为什么不需要锁

这里的“获取快照”是消费者自己的线程读取共享数据，再保存为自己使用的值。
数据来自生产者，不代表生产者正在写消费者的私有对象。

以当前接口为例：

```cpp
// 两行都由同一个消费者线程执行。
const auto imu_input = blackboard.read(blackboard.imu_state);
const auto target_input = blackboard.read(blackboard.target);

// 随后使用这两个本地值完成本轮计算。
```

生产者修改黑板中的对象，消费者执行读取并写入自己的副本。复制完成后，
生产者继续更新黑板，不会改变已经获得的值快照。

因此，私有输入无需互斥锁的条件是：

- 输入获取和后续使用由同一个组件线程完成。
- 其他线程不直接修改该组件的输入和内部状态。
- 快照中的数据独立存在，或持有明确有效期的只读缓冲。

如果另开一个“搬运线程”持续修改组件的 `inputs_`，同时组件线程读取 `inputs_`，
那么它就重新成为共享对象，需要同步。这会把竞争从黑板转移到组件内部，不能达到预期目的。

按值复制包含指针或共享句柄的结构体，也不代表其指向的数据被复制。
对于图像等大数据，需要明确缓冲所有权和有效期，保证消费者使用期间不会被覆盖。

跨线程同步发生在交接阶段，私有快照把计算阶段与共享数据的变化隔离开。
这个划分符合 [C++ 的数据竞争与同步规则](https://eel.is/c++draft/intro.races)。

## 5. 黑板的语义：最新状态与逐条消息

### 最新状态

目标坐标、姿态、预测增量等通常适合表达为“当前可用的最新状态”。
这种通道允许消费者重复使用同一个结果，也允许生产者覆盖尚未被读取的中间结果。

333 Hz 的控制循环使用同一份相机结果多次是正常情况，不要求严格交替执行“写一次、读一次”。
生产者较慢时消费者使用旧结果，生产者较快时消费者可以跳过中间状态。

消费旧结果需要结合输入有效性和时间信息判断。允许复用旧状态，不能解释成允许无限期使用失效状态。

### 逐条消息

需要逐条保存的记录、事件或命令需要单独判断顺序和丢失语义。
最新值槽位不能代替保存每一条消息的队列。

| 通道语义 | 适合的数据 | 处理不过来时的行为 |
| --- | --- | --- |
| 最新值 | 目标位置、姿态、控制状态 | 覆盖中间状态，读取当前可用结果 |
| 有界消息队列 | 逐条记录、事件 | 按约定丢弃、覆盖、降采样或回压 |

每条通道明确发布者、消费者、所有权、数据有效期以及丢失是否允许。
推荐让一个逻辑状态流有明确的负责发布者，避免多个组件无意覆盖彼此的结果。

## 6. 小型数据使用原子发布

当前视觉目标由 `detection::Point` 表示，包含 `x`、`y` 两个浮点值。
现有 `AtomicValue<detection::Point>` 整体发布和读取坐标，适合这一类独立的小型状态。

### 关联字段整体读取

`x` 和 `y` 是一份目标结果，作为同一个原子对象交接，可以避免读到不同次发布的坐标组合。
把两个字段拆成独立的原子变量，只能保证各字段分别原子访问，不能保证两次读取来自同一帧。

如果以后增加有效标志、源时间戳或帧序号，需要重新确定哪些字段必须保持一致。
分成多个原子对象发布，不会自动形成整组快照。

### 在目标平台确认无锁

`std::atomic<T>` 不保证任意类型都无锁。类型增大后，原子操作也可能由内部锁实现。
现有封装使用：

```cpp
static_assert(std::atomic<T>::is_always_lock_free);
```

保留这一检查，让真实目标的交叉编译确认能力。主机上的大小、对齐和无锁能力不能替代目标平台结论。
适用于原子封装的值类型还需要满足 `std::atomic<T>` 对类型的要求。

增加元数据后，如果整个快照超出目标平台支持的无锁原子范围，改用合适的缓冲交接，
不能默认把整个大结构体放进 `std::atomic` 就仍然无锁。

### memory_order_relaxed 的适用范围

当原子对象仅传递自身包含的完整值时，例如独立的目标坐标，现有 `memory_order_relaxed`
可以提供所需的原子读写，不必额外借它同步其他内存。

如果原子值被用作另一个非原子对象的“数据已准备好”标志，就涉及额外的发布、获取和生命周期协议。
仅对标志做原子访问不足以保证外部数据安全；即使选择了合适的内存序，也仍需保证读取期间数据不被复用。

## 7. 普通快照、非阻塞读取与多缓冲

黑板是统一的数据入口，不要求所有槽位使用同一种同步实现。

| 方式 | 能解决的问题 | 仍需考虑的边界 |
| --- | --- | --- |
| 整体原子值 | 小型状态交接无需互斥锁 | 类型、对齐、目标无锁能力和关联字段一致性 |
| 短锁复制快照 | 在复制期间保护完整数据 | 消费者仍可能等待锁，持锁线程可能被抢占 |
| `try_read` 加本地缓存 | 取不到锁时消费者继续运行 | 继续使用旧输入，检查有效期；其他读写路径仍可能等待 |
| 单生产者、单消费者三缓冲 | 通过所有权交接隔离读写中的缓冲 | 拓扑限制、缓冲复用时机和正确的原子交接协议 |

### 当前 Latest 的锁覆盖范围

`Latest<T>::read()` 在锁内复制 `Snapshot`，按值返回时释放锁。
消费者随后使用返回值，不会在整个 `update()` 期间继续持有这把锁。
`write()` 同样只应负责发布快照，不在锁内执行算法、文件写入或设备调用。

这已经避免了整轮更新被锁包住，但没有消除复制时的互斥。
临界区短可以减少等待机会，不能单凭这一点宣称最坏等待时间已有保证。

### try_read 的语义

候选接口 `try_read(snapshot)` 尝试获取锁，成功时复制完整快照，失败时保持组件上次的输入不变。
它用于让关键消费者不等待持锁方释放锁，不保证这一轮一定获取到新结果。

首次尚未取得输入、输入无效、输入过期时的行为由对应组件明确处理。
取锁失败不能通过更新时间戳把旧输入伪装成新数据。

### 三缓冲的所有权

对于单生产者、单消费者的最新状态通道，可以考虑三个预分配缓冲：

```mermaid
flowchart LR
    W["生产者持有：写缓冲"] <-->|原子交换所有权| M["待交接缓冲"]
    M <-->|原子交换所有权| R["消费者持有：读缓冲"]
```

生产者只修改自己的写缓冲，消费者使用自己的读缓冲，第三块缓冲用于交接。
生产者可以继续发布，消费者也可以继续使用已持有的数据，不需要在耗时计算期间持有互斥锁。
消费者交回缓冲之前，生产者不能覆盖该读缓冲。

这个机制仍有原子操作和缓存同步成本。“无锁”也不等于整轮工作已经拥有确定的执行时间上界。
仅使用两个缓冲和一个原子下标，不能自动保证缓冲在消费者读取期间不被重新写入。

三缓冲的上述模型针对单生产者、单消费者。多个消费者需要独立接收端或另外设计所有权协议，
不能把同一个单消费者读端直接交给多个线程。
参见[三缓冲生产与消费模型](https://docs.rs/triple_buffer/latest/triple_buffer/)；该资料用于说明模型，不代表引入其库依赖。

## 8. 输入时间、序号与一致性

组件每轮获取依赖后，固定使用这轮输入完成计算，避免计算中反复读取同一槽位而混用不同次发布的值。
但逐个读取多个槽位，并不保证它们来自同一时刻。

例如姿态、目标和预测增量可能分别来自不同时间。算法需要严格对应时，
通过源时间戳、帧序号或成组发布的快照建立关系；有时间对齐需求时还需要明确时钟来源及转换方式。

需要区分几种信息：

| 信息 | 含义 |
| --- | --- |
| 源时间戳 | 采样或结果生成的时间，用于判断数据年龄 |
| 源序号或帧号 | 判断是否是新的源数据，以及结果对应哪份输入 |
| 发布时间 | 本次向某个通信槽位发布的时间 |
| 发布计数 | 向该槽位写入的次数 |

重复搬运同一份源数据会产生新的发布时间和发布计数，但不代表源数据变新。
当前 `Latest::Snapshot` 的 `sequence` 和 `published_at` 在每次 `write()` 时更新，
它们本身不能自动当作相机帧号或 IMU 采样时间。

原子坐标槽位目前没有附带时间戳。无效坐标可以表达未检测到目标，
但不能单独判断一个看起来有效的坐标是否已经陈旧；若控制需要此判断，应同时设计元数据的交接方式。

## 9. 文件 I/O 与控制周期隔离

周期性的文件同步不放在控制更新的执行路径中。`fsync()` 会等待设备完成同步，
将它放进控制周期，就会把存储延迟直接带进控制周期。
参见 [Linux fsync 文档](https://man7.org/linux/man-pages/man2/fsync.2.html)。

隔离范围不只包括 `fsync()`。文件打开、写入、刷新、压缩、复杂格式化，以及涉及动态分配或锁的日志调用，
都需要根据其耗时和阻塞行为决定执行位置。

建议的数据路径为：

```text
控制线程：取得输入 → 计算 → 输出控制量 → 尝试提交记录
记录线程：取出记录 → 格式化或编码 → 写入文件 → 按策略同步
```

控制线程使用预分配的有界记录通道，提交失败时按明确策略处理，不能在队列满后隐式等待记录线程。
丢弃、覆盖或降采样时保留相应统计；这些统计的提交也不重新引入阻塞日志。
图像等大数据使用明确所有权的缓冲或句柄，不能在提交后立即复用仍被记录线程使用的内存。

如果要求每条记录都不丢失，且存储长期慢于生产速度，就无法同时保证有限缓冲和生产者永不等待。
这需要调整吞吐、记录量或回压策略，不能用一个更大的队列永久解决。

后台 I/O 仍可能通过 CPU、内存、存储和内核资源竞争影响控制调度。
移到后台隔离了直接等待，最终效果还要在板端写盘压力下确认。

## 10. 接口可见性与具体类的封装

引入 `Component` 的一个目的，是让运行管理代码通过共同接口持有组件，不依赖每个具体类的定义。

共享接口放在消费者需要的功能头文件中。`Servo` 这类内部类型可以继续留在 `servo.cpp`；
`DutyMapping` 如果通过组件接口被使用，其完整定义也可以留在实现文件中。
在共享功能头中声明工厂函数，由对应实现文件构造具体对象并返回组件接口的所有权句柄。

因此不需要为了统一调度给每个内部类各建一个头文件。
同时，只有在执行边界上需要被独立调度的对象才需要实现组件接口；
四个舵机由同一个映射组件管理时，内部四个 `Servo` 可以继续作为普通成员。

通过基类持有并销毁具体组件时，接口提供虚析构函数。
线程由外层运行管理逻辑持有，并在组件销毁之前停止和等待退出，避免在派生对象已销毁后继续调用虚函数。

统一接口的错误返回和生命周期状态仍需单独设计。
现有 PWM 输出返回的 `std::expected<void, pwm::Error>` 不能在接入组件接口时被忽略；
适配层负责设备错误，运行管理逻辑需要知道组件应继续、降级还是停止。
这不意味着所有领域组件都要依赖 PWM 专用错误类型。

| [servo.cpp](servo.cpp) 中的 `DutyMapping` | 内部更新姿态、控制、预测、舵机映射并写 PWM | 当前仍是组合调用，预测对象尚未通过结果通道与映射解耦 |
| 通用 `Component`、运行管理器 | 当前 control 文件中尚未提供 | 属于待落地的接口和生命周期设计 |
| `try_read`、三缓冲 | 当前黑板尚未提供 | 候选机制，根据具体通道需求选择 |

本文记录设计，不将候选机制视为已有实现，也不作为硬件性能已经验证的证据。

## 12. 后续实现时需要确定与验证的事项

先明确组件边界及执行线程，再为每条依赖确定槽位、发布者、消费者、数据新鲜度和允许丢失的语义。
优先沿用小型原子值通道，按需求为较大数据选择短锁、非阻塞读取或所有权交接，避免统一套用一种机制。

需要进一步确定的接口细节包括组件错误返回、启动失败处理、退出顺序、过期输入行为、
周期超时策略，以及需要成组发布的数据范围。这些内容不由本文提前固定为已实现的接口。

周期组件使用单调时钟安排节拍。过期周期采用跳过、补跑还是其他处理方式，应结合控制语义确定，
避免无意形成持续追赶的忙循环。停止方式和外部调用也要纳入响应时间检查。

验证时区分三个层面：

| 层面 | 需要确认的内容 |
| --- | --- |
| 主机行为 | 快照独立性、交接一致性、停止与退出、输入过期和队列满时的行为 |
| 真实目标编译与链接 | 新实现参与实际目标，原子无锁检查和工具链能力满足要求 |
| 板端运行 | 控制周期最大与高分位耗时、超期次数、输入年龄、队列水位和丢弃数量 |

板端验证覆盖视觉处理、记录写入和文件同步同时运行的负载。
采用无锁数据结构或通过主机验证，都不能单独证明驱动调用和整条控制链已经满足时限。

### 获取自身快照与 update 循环

`Component::run()` 固定执行 `capture_inputs()`、`update()`、`publish_outputs()`。
`ServoComponent::capture_inputs()` 在自己的工作线程里，把黑板坐标整体复制到 `inputs_.target`。
`update()` 只读取这份私有输入和自己的配置，`publish_outputs()` 再调用 PWM 接口。
这三个阶段没有独立的搬运线程，组件输入和内部状态也没有额外的互斥锁。

每个组件有自己的周期。循环按单调时钟安排节拍，执行超时后跳过已经错过的周期，并记录统计。
停止是协作式的；普通 `sleep_until()` 不能被停止请求直接唤醒。
`max_tick_time` 统计一次获取、计算和发布的耗时，不代表已经测得完整的唤醒抖动或硬件最坏延迟。

### 具体类保持在 cpp，宏生成工厂注册入口

`ServoComponent` 的完整定义只存在于示例的 `servo.cpp`。文件末尾：

```cpp
DART_EXAMPLE_COMPONENT(register_servo, ServoComponent, "servo")
```

宏生成普通函数 `register_servo(Registry&)`，函数向注册表加入创建该类型的工厂。
示例采用 `(Context&, const ComponentSpec&)` 作为工厂适配的构造入口，
具体组件在构造时解析并保存自己的配置；这不是要求工程中所有内部类具有相同构造函数。

`register_builtin_components()` 显式调用各注册函数，保证静态库中的对应实现参与最终链接。
这里没有全局静态自动注册，也没有为 `ServoComponent` 或 `VisionComponent` 单独建立头文件。
需要其他构造参数的类型，可以通过 `Registry::add()` 提供自己的工厂适配函数。

### 初始化、线程与数据所有权

程序先创建共享资源和全部组件，再按配置列表顺序初始化和启动。
列表中的顺序只约束启动，不会在每轮更新时建立等待屏障。
为了保持本示例的一份坐标通道和一份 PWM 输出只有一个负责发布者，当前限制每个类型只有一个实例。
这份简化 YAML 没有实现 `start_after` 依赖图，也不提供动态库加载。

全部工作线程停止并退出后，主线程才逆序调用 `shutdown()`、读取统计和模拟 PWM 状态。
`ServoComponent::on_shutdown()` 输出中位脉宽，并把输出错误返回管理层。
初始化或部分线程启动失败时，应用析构仍负责停止已启动线程并清理已初始化组件。

主线程退出等待使用互斥锁和条件变量；组件故障时通知这条事件通道。
这把锁不用于坐标交接，也不在正常获取快照、计算和发布的路径中。
控制线程没有格式化输出或文件写入，终端统计在线程退出后输出。

该示例只传输坐标，没有同时携带源时间戳或帧号，因此没有演示生产者停更后的过期判断。
接入真实设备时，仍需补充输入年龄、缓冲所有权和驱动时限约定，不能把模拟 PWM 的耗时视为硬件证据。

### 主机构建与运行

在仓库根目录执行。需要支持 C++23 的编译器和主机 `yaml-cpp`：

```sh
cmake -S tools/component_example -B /tmp/dart-component-example-host -DCMAKE_BUILD_TYPE=Debug
cmake --build /tmp/dart-component-example-host --parallel
ctest --test-dir /tmp/dart-component-example-host --output-on-failure
/tmp/dart-component-example-host/component_example tools/component_example/components.yaml
```

程序默认运行 250 ms，然后停止并输出两个组件各自的更新次数、跳过周期数和最大单轮耗时。
这些次数受线程调度影响，不承诺恰好达到理论次数。

不读取 YAML 时，也能使用内置的同等配置：

```sh
/tmp/dart-component-example-host/component_example
```

### 交叉编译与仓库目标

核心组件不依赖 YAML。交叉构建默认关闭 YAML 读取，使用内置配置；
主机构建也可以通过 `-DDART_COMPONENT_EXAMPLE_WITH_YAML=OFF` 关闭这一依赖。

```sh
cmake -S tools/component_example -B /tmp/dart-component-example-riscv \
  -DCMAKE_TOOLCHAIN_FILE="$PWD/cmake/toolchain-riscv64-musl.cmake" \
  -DK230_TOOLCHAIN_DIR=/path/to/toolchain/bin \
  -DDART_COMPONENT_EXAMPLE_WITH_YAML=OFF -DBUILD_TESTING=OFF
cmake --build /tmp/dart-component-example-riscv --parallel
```

独立交叉构建用于检查 RISC-V 源码编译及静态 ELF 最终链接，不等同于 RT-Smart 板端运行验证。
仓库根 CMake 也注册了按需构建的 `component_example` 目标；从根工程交叉构建时会连接
`k230_rtos_app`，沿用工程的 SDK 和链接设置。根工程默认不为这个可选目标引入 YAML 依赖，
需要时显式启用 `DART_COMPONENT_EXAMPLE_WITH_YAML` 并提供对应平台的库。
