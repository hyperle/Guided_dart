# v2 架构说明

当前工程约束见 [AGENTS.md](../AGENTS.md)。本文描述职责和设计目标；
历史接口示例不能覆盖当前模块接口，也不授权执行旧迁移任务。

本仓库是 K230D/K230 RT-Smart 的**用户态业务代码仓库**，不负责烧录或修改板端 BSP。当前已实现相机、IMU、检测、录像、应用编排、视觉坐标映射和启动器；完整飞行控制仍是设计目标。实际入口和文件以各模块 README 与源码为准。

## 1. 工况与目标

最终设备是无动力抛体/滑翔体，使用相机识别引导灯和装甲板，结合 IMU、姿态控制和舵面执行机构完成末段导引。主要工况分为：

1. **启动/重捕获**：不知道目标位置，必须全图扫描并用时间一致性确认，宁可暂不输出目标，也不能把坏点或反光当成目标。
2. **跟踪/接近**：目标尺寸随距离增大，使用预测 ROI 和尺度状态降低扫描开销，同时在丢帧、出框和干扰物出现时可退化到重捕获。
3. **飞行控制**：外环修正航向/落点，内环跟踪姿态，末段在可行性约束下逐渐转向终端姿态，不能把“机头对准目标”误当成“速度方向命中目标”。

视觉、IMU、控制和录像必须以时间戳、有效位和明确的所有权连接；任何一层都不能用默认值掩盖数据失效。

## 2. v2 的分层和依赖方向

```
L4  领域/策略层（纯 C++）
    状态机、检测跟踪策略、观测器、控制律、参数策略、诊断事件
             ↓ 依赖抽象接口，不认识 SDK、文件系统和线程库细节
L3  设备/运行时抽象（纯 C++）
    相机、IMU、舵机、计时器、存储等接口；通过构造注入总线和资源
             ↓ 由适配器实现
L2  防腐层 ACL（C++ 适配器）
    把 K230 SDK 的 C API、句柄、返回码、缓存同步和所有权翻译成稳定接口
             ↓ 只在边界处包含厂商头文件
L1  BSP/HAL/MPP（厂商 C）
    SDK 原始头文件和库；不在本仓库中重写或“美化”
```

当前相机的数据面与 SDK 边界使用 C，检测与业务编排使用 C++，编码等组件按实际接口选择语言。
不以“数据面”或“控制面”的名称强制迁移实现语言；性能结论需要复制次数、分配次数和板端时序证据。
这套设计吸收领域驱动设计、依赖倒置和防腐层的共同原则：先让领域对象表达状态和不变量，再由边界适配外部系统；所有权、时间和错误都显式传递；硬件替换不应迫使算法层改写。外部仓库只能作为思想参考，不作为本仓库依赖或逐文件模板。

### 2.1 依赖规则

- 业务层不能包含 K230、MPP、POSIX 设备头文件，也不能直接调用 `ioctl`、`mmap`、`vb_*`。
- L3 只依赖自有抽象；驱动对象通过构造函数或 `create/init` 注入总线、时钟和资源。
- L2 是唯一允许翻译厂商返回码、处理 cache/DMA 同步和管理 SDK 句柄的地方。
- L1 保持 C；不得为了“统一风格”把厂商 SDK 改成 C++。
- C ABI 只使用固定宽度整数、指针和显式 POD；C++ 异常不得跨 ABI。
- 每个缓冲区必须写清所有者、读写方、有效期、stride、cache 属性和同步动作。

### 2.2 语言与错误契约

- C 数据面使用 C11；状态码和输出参数按实际模块的 C ABI 定义。
- C++ 使用 C++23；需要携带失败原因时使用模块自身的错误类型和 `std::expected`。
  当前相机使用定长 `CameraError`，检测、录像等有各自错误类型；不强制引入旧计划中的统一 `DartError` 或多态错误指针。
- 热循环中的“没有目标”是正常结果，用枚举/`bool` 表达，不伪装成错误。
- 叶子函数只返回错误，不重复打印；能决定恢复动作的边界统一记录一次结构化错误。
- 初始化失败拆成 `create/init/start`，不在构造函数中打印、退出或抛异常。
- 在交叉工具链探针和实际链接验证通过前，不假设 `std::expected` 或 `-fno-exceptions` 可用。

## 3. 目录职责

封装以减少理解成本为准。配置、结果、内部状态和辅助步骤应跟随所属职责；
只有独立消费者、资源生命周期或跨模块契约支持时，才建立新的文件或调用层。
一次操作中的临时计算直接留在操作内，例如曝光范围检查、钳位和单位换算属于
相机的曝光设置方法，不需要额外的规划器和规划结果。无状态操作使用普通函数，
对象通过私有状态和方法维护实际不变量。

参考 [RMCS 的 TD](https://github.com/Alliance-Algorithm/RMCS/blob/a27e3d14c36ef8d780287e154b32ed4a70bbbdc9/rmcs_ws/src/rmcs_core/src/controller/adrc/td.hpp)
把 Config、State、Output 与计算放在一起，以及
[librmcs 的设备扫描器](https://github.com/Alliance-Algorithm/librmcs/blob/47313cea064750c8fc42c822083ebe9df7179dbd/host/src/transport/usb/device_scanner.hpp)
将扫描结果和诊断类型收在实现内部的组织方式。这里借鉴职责边界，不引入其框架依赖。

实际布局（2026-10 更新）：`src/` 全部是 L4 调用与策略层，二级目录按功能划分。
下层接口与实现统一位于 `include/firmware/src/`；库目标由 `include/CMakeLists.txt`
声明，业务目标由 `src/CMakeLists.txt` 声明。下层库不得反向包含 `src/`。

```
src/                        L4 调用、编排与策略
  dart_entry.cpp            唯一入口，将板级工厂注入启动流程
  startup/                  参数、服务组装、故障隔离与运行顺序
  vision/                   采集生命周期、识别与帧分发
  recording/                录像配置、启停决策与租约排空
  diagnostics/              相机错误字段与检测 CSV 字段映射
  detector/                 连通域、灯、装甲板与 ROI
include/firmware/src/    下层公开接口与实现库
  camera/                   相机帧类型、接口与 ACL/C 数据面
  imu/、spi/                IMU 抽象、估计器与硬件适配
  board/                    具体设备工厂和板级初始化
  system/                   时钟、停止信号与 launcher 退出标记
  logging/、storage/        日志、通用 CSV 写入与目录操作
  streaming/                有界灰度复制、C11 JPEG、压缩/上传线程与 SDIO ACL
  recorder/                 录像服务：图像队列、相机租约与生命周期
    async/                  元数据有界队列与写线程
    encoding/               内存 PNG 编码
    storage/                轮次保留、空间预算、图片与事件文件
runtime/
  launcher/                 平台无关 C11 自启器 + startup.list 母版
  imu/                      现有独立采样服务（采样与诊断行为）
cmake/                      交叉工具链配置（链接脚本取 SDK 的 libs/mk/link.lds）
.script/                    构建、部署、清理与回归检查
docs/                       设计、标定、调试和验收契约
```

L4 通过公开接口调用下层实现，不包含 SDK 或 POSIX 实现头文件。
`startup/` 组织组件的运行顺序；`vision/` 决定帧的流向；`recording/` 决定录像何时启停；
`diagnostics/` 定义业务字段。线程、缓冲、文件同步和设备寄存器不属于这些调用模块。
参数帮助文本和参数错误的标准输出属于 CLI 交互，保留在参数解析模块。

检测器通过相机的只读帧类型头文件获取帧数据契约，不链接相机 ACL 或 K230 后端。
C++ 按需使用 `.hpp` 声明和 `.cpp` 实现，普通实现独立编译并参与链接；不要求头文件与源文件一一配对。入口只连接 `board/` 提供的工厂与
`startup/` 调用流程，具体初始化由下层板级适配器完成。
IMU 采样和后续控制任务按各自频率运行，不随相机逐帧循环调度。
launcher 负责进程监督，L4 启动流程负责进程内部的组件编排。

启动链路的完整设计（清单语义、所有权、日志布局、v1 教训）见
[`LAUNCHER_DESIGN.md`](LAUNCHER_DESIGN.md)。

目前不要因为目录在文档中出现就创建空壳文件；实现任务应先选择一个垂直切片，补齐接口、CMake、日志和验证，再进入下一个模块。应用之间不得共享可变全局状态。

## 4. 运行时数据流和所有权

```
VICAP/传感器（ACL）
       ↓ 带时间戳、stride、cache 状态的输入
相机帧缓冲 → 候选提取/扫描/ROI 测量
       ↓ 目标坐标
检测与跟踪策略（C++） → 观测器/控制器（C++）
       ↓ 归一化力矩或舵偏请求
控制分配/舵机 ACL → 实际 PWM 与反馈
       ↘ 录像/取证数据面（固定队列、异步写盘）
```

- 运行态禁止逐帧 `malloc/free/new/delete`；启动期一次性申请并记录工作区高水位。
- 帧槽使用显式状态（例如 `free → captured → processing → queued → released`），一个时刻只有一个释放责任；不得依赖“看起来没有锁”来掩盖双重归还。
- 视觉线程不做文件 I/O；录像/诊断用有界队列，队列满时按策略丢样本并累计计数，不能阻塞采集或控制环。
- 时间统一使用单调时钟。视觉、IMU、控制和执行器记录采样时间、处理时间、数据年龄及 `valid/stale/saturated/gap` 标志。
- 观测、预测和控制失败时必须走安全退化路径；NaN、越界窗口、失效句柄不可进入舵面。

## 5. 验证策略

本仓库不做“为了主机测试而模拟整块板子”的工作。验证分三层：

1. **主机可重复验证**：只覆盖纯算法、固定尺寸数学、C ABI、状态机和错误传播；使用合成输入或显式 fake 接口，不向业务代码加入板端兼容分支。
2. **交叉构建验证**：用仓库的 RISC-V 工具链和 SDK 头/库检查 ABI、链接、段大小和 `-fno-*` 约束；构建产物是可拷贝到 RT-Smart 用户态的 ELF。
3. **板端验证**：验证 RVV、cache/DMA、MPP、真实曝光、传感器时序、舵机响应、录像和内存高水位。性能和视觉质量的结论只能来自板端日志/样本，不能由主机纳秒数替代。

每轮实现都应留下：变更范围、主机结果（若适用）、交叉构建结果、板端命令/参数、原始日志和失败样本。没有真实硬件时，文档只能写“待板端验证”，不能写成已通过。

## 6. Agent 工作顺序

1. 先读 `AGENTS.md` 和任务相关模块的当前说明；设计文档用于理解目标，历史重构计划只作背景。
2. 检查当前 Git 状态和实际目录；不要根据 v1 文档假设文件存在。
3. 先定义边界、数据所有权、错误/正常否定结果和日志字段，再写代码。
4. 修改一个垂直切片并在相应层验证；不要顺手重写 SDK、固件或无关模块。
5. 任何占位参数必须显式标为 `UNVALIDATED`，未经标定不能进入真实控制通路。
6. 文档中的历史数据只能作为假设或待复现实验，新增结论必须带来源、条件和日期。

## 7. 禁止事项

- 不在 `src/` 中实现设备工厂、线程、文件系统或 SDK 适配；L4 按功能调用
  `include/` 中的下层库，不再建立包揽所有职责的 `application/` 目录。
  不把具体相机实现作为检测算法的依赖，也不要把 v1 的 `self_guiding_dart` 整体搬回来。
- 不要出现第二个持有 VICAP/VB 的进程：识别与录像必须在 `dart_app` 这一个 ELF 内
  串联（v1 实测多实例抢资源必死），清单里也不能放第二条 payload。
- 不要把外部仓库（包括 v1 或 RMCS）当作本仓库的依赖；只提炼设计原则并在本仓上下文重写。
- 不要用主机兼容层伪造 MPP/VICAP/VENC 行为；硬件假设要由 ACL 和板端探针验证。
